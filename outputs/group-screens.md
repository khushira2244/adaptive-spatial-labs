# Adaptive Spatial Labs — Grouped Screen Plan

Yes bro — exactly. We should **not try to design all 46 screens individually at once**.

The right approach is to group screens that share the same data, navigation, backend domain, and user flow. Then we finish one group end-to-end: **frontend screens + backend entities/APIs + states + permissions + testing**, before moving to the next group.

I would divide Adaptive Spatial Labs into **7 connected product groups**.

### Group 1 — Identity + Project Foundation
These belong together because they establish who the user is and what project they are entering.

Includes:
- Landing
- Sign Up
- Login
- Home / Projects
- New Project — Basics
- New Project — Structure
- New Project — Inputs
- New Project — Editors
- New Project — Review/Create
- Project Created / Setup

Backend for this group:
```text
User
Organization
Project
ProjectOwner
ProjectEditor
ProjectVisibility
ProjectStructure
SourceConnection
UploadedSource
```

This should be our **first complete frontend + backend group**.

---

### Group 2 — Project Model + Configuration
Everything here defines what the project actually contains.

Includes:
- Imported Model Review
- Project Main Workspace
- Layer Configuration
- Architecture Object Library
- Object Inspector
- Source / Evidence View
- Product ↔ Architecture Mapping

Backend:
```text
LayerDefinition
ObjectType
ArchitectureObject
RelationshipType
Relationship
Product
Feature
Requirement
Source
Evidence
Mapping
```

This is the **core model of Adaptive Spatial Labs**.

This group is extremely important because every later feature sits on top of it.

---

### Group 3 — Views + Spatial Representation
These screens all answer:

> How should this existing model be shown?

Includes:
- Create View
- View Spatial Configuration
- View Suggestions
- Saved View / Preview

Backend:
```text
View
ViewLayer
ViewObject
ViewRelationship
SpatialLayout
VisualConfiguration
Suggestion
SelectedSuggestion
CustomVisualFeature
```

And here we implement the rule we decided:

```text
Built-in suggestion
OR
User-created suggestion
OR
AI-generated suggestion
        ↓
USER SELECTS
        ↓
View configuration
```

Nothing auto-applies.

This group controls:
- depth
- height
- scale
- colors
- grouping
- focus behavior
- labels
- relationships
- visibility
- spatial positioning

---

### Group 4 — Presentation + Audience
This is different from normal View creation because now the architect decides **who will see what**.

Includes:
- Presentation Creation
- Presentation Visibility
- Presentation Stages
- Invite People/Teams
- Schedule / Start Meeting

Backend:
```text
Presentation
PresentationStage
PresentationAudience
PresentationPermission
PresentationInvite
PresentationView
MeetingSchedule
CalendarLink
```

Flow:

```text
Project
  ↓
View
  ↓
Presentation
  ↓
Audience
  ↓
Visibility / permissions
  ↓
Meeting
```

This is where:

```text
Architect → Backend
Architect → Frontend
Architect → Product
```

becomes concrete.

---

### Group 5 — Live Collaboration + My Space
All of these belong together because they are one live-session experience.

Includes:
- Meetings Home
- Pre-Meeting Preparation
- Live Meeting — Presenter
- Live Meeting — Participant
- My Space During Meeting
- Raise Point
- Shared Question state

Backend:
```text
Meeting
MeetingParticipant
MeetingRole
SessionState
SharedFocus
SharedSelection
PointerState
PrivateWorkspace
PrivateAnnotation
SharedAnnotation
RaisedPoint
```

Important state split:

```text
PROJECT STATE
persistent

SESSION STATE
shared during meeting

PERSONAL STATE
private to user
```

And the flow:

```text
MY SPACE
PRIVATE
   ↓
READY TO SHARE
   ↓
RAISE POINT
   ↓
SHARED SESSION
```

This should be treated as **one group**, not many unrelated screens.

---

### Group 6 — Discussion → Decision → Work
These are all stages of the same conversation lifecycle.

Includes:
- Trade-Off Discussion
- Decision Capture
- Proposal / Architecture Modification
- Current vs Proposed Compare
- Decision → Action / Ticket
- Meeting Summary

Backend:
```text
DiscussionTopic
Question
Tradeoff
TradeoffOption
Decision
Proposal
ProposedChange
ActionItem
TicketReference
MeetingSummary
```

The canonical flow:

```text
QUESTION
   ↓
DISCUSSION
   ↓
TRADE-OFF
   ↓
DECISION
   ↓
PROPOSAL / CHANGE
   ↓
ACTION
   ↓
TICKET
```

This should be one backend domain because otherwise the context will become fragmented.

---

### Group 7 — Readiness + Personal/Administration
These consume everything generated by the previous groups.

Includes:
- Product / Feature Readiness
- Discussion History / Decision Timeline
- Global My Space
- Inbox
- Integrations
- Project Settings
- Profile / Settings

Backend:
```text
FeatureReadiness
ReviewRequirement
RoleReview
DiscussionCoverage
InboxItem
Notification
Integration
UserPreference
ProjectSetting
```

This group is mostly **derived information + administration**.

It should come later, because readiness cannot exist properly until questions, decisions, mappings, and meetings exist.

---

# So the 46 screens reduce to 7 real systems

```text
1. Identity + Project Foundation

2. Project Model + Configuration

3. Views + Spatial Representation

4. Presentation + Audience

5. Live Collaboration + My Space

6. Discussion + Decision + Work

7. Readiness + Administration
```

That is much easier to reason about.

And for implementation, I would go even further.

## First complete level

Build Groups **1 + 2** together.

That gives us:

```text
Signup
↓
Home
↓
Create Project
↓
Add structure/input
↓
Project created
↓
Review/build model
↓
Layers
↓
Objects
↓
Relationships
↓
Product ↔ architecture mapping
```

At that point Adaptive Spatial Labs has a **real project backend and real frontend foundation**.

Then:

## Second level

Group **3**:

```text
Model
↓
Create View
↓
Spatial configuration
↓
Suggestions
↓
User selects
↓
Saved View
```

Now we have the real spatial product.

Then:

## Third level

Groups **4 + 5**:

```text
View
↓
Presentation
↓
Audience
↓
Meeting
↓
Shared session
↓
My Space
```

Now collaboration works.

Then:

## Fourth level

Groups **6 + 7**:

```text
Discussion
↓
Trade-off
↓
Decision
↓
Ticket
↓
Readiness
```

Now the entire business value closes.

So I would **not think in terms of 46 screens anymore**.

Think:

> **7 product domains, implemented in 4 end-to-end levels.**

That will make both our frontend design and backend architecture much more coherent.
