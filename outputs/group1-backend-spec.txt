PROJECT: Adaptive Spatial Labs

We are building a professional mixed-reality software architecture
collaboration platform for Meta Quest.

The frontend is built in Unity/C#.

There is NO React/web frontend in the current V1.

The backend must expose normal client-agnostic REST/JSON APIs so the
Unity Quest application can consume them cleanly.

Later, if we ever add another client, the backend should not require redesign.

==================================================
IMPORTANT: UNITY / META QUEST CLIENT
==================================================

The primary frontend is Unity/C# running on Meta Quest.

The backend must NOT depend on:

- browser cookies
- HTML forms
- React
- browser session state
- localStorage
- browser-specific redirects
- browser-only authentication assumptions

Unity should be able to call APIs using normal HTTP requests.

Use:

Authorization: Bearer <access-token>

All API responses must use predictable JSON structures that map cleanly
to C# DTOs.

Use:
- camelCase JSON
- UUIDs represented as strings
- ISO-8601 timestamps
- stable string enum values
- explicit nullable fields
- predictable response structures

Avoid unnecessarily dynamic JSON structures in public API responses.

Build this as a MODULAR MONOLITH.

We want one backend deployment, but the code must be divided cleanly
by product domain.

DO NOT create:

- one giant app.service.ts

- authentication logic copied across routes

==================================================
PROJECT CREATION WIZARD
==================================================

The Unity frontend has this creation flow:

1 Project Basics
2 Project Structure
3 Existing Inputs
4 Editors
5 Review & Create
6 Project Created celebration
7 Proceed

Do NOT treat the five wizard screens as five unrelated backend creation
operations.

The Unity client may keep the incomplete wizard state locally.

When the user selects CREATE PROJECT on Review & Create, send one
complete project-creation command.

Conceptual example:

{
  "name": "Payments Platform",
  "description": "Core payment platform architecture",
  "organizationId": "...",
  "projectType": "PRODUCT_SYSTEM",
  "visibility": "RESTRICTED",

  "structure": {
    "templateKey": "PRODUCT_SYSTEM",
    "layers": [
      {
        "name": "Product",
        "sortOrder": 1
      },
      {
        "name": "Service",
        "sortOrder": 2
      }
    ]
  },

  "editorUserIds": [],

  "sources": []
}

Implement project creation using a PostgreSQL transaction.

Transaction must:

1 create Project
2 set creator as owner
3 add project editors
4 create ProjectStructure
5 create project layers
6 create/attach source metadata records
7 commit

If a critical operation fails:

ROLLBACK EVERYTHING.

The frontend must receive success only after the transaction commits.

This ensures the Project Created celebration screen reflects a real,
successfully persisted project.

==================================================
MODULARITY RULES
==================================================

This is critical.

Adaptive Spatial Labs will grow substantially.

Do not place unrelated capabilities on the same page/module/file.

Backend modules must remain independent and composable.

If one file becomes responsible for multiple product concerns, split it.

Examples:

Auth service handles authentication.
It does not create projects.

Project service handles project orchestration.
It does not parse files.

Source service handles source metadata/storage.
It does not perform AI extraction.

Preferences service handles preferences.
It does not control Quest rendering.

Shared utilities must contain genuinely cross-cutting concerns only.

Do not move domain business logic into "utils".

Avoid circular module dependencies.

Prefer explicit small modules over premature generic abstractions.
